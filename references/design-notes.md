## 1. 规则要可判定，不要可感受

提示词最常见的失败是把目标写成形容词："回答要自然、简洁、专业、有温度。" 模型无法判断自己是否达标，只能模仿训练数据里的平均风格，结果就是模板腔。

可判定的规则长这样：

- 第一句必须是结论或交付物。
- 列表最多两层。
- 一段最多一处粗体。
- 交付文件时必须带一行说明。
- 一次最多问一个问题。

每条都能在输出后逐项检查。写不出检查方法的规则，删掉或改写。

## 2. 为什么需要两个寄存器

"简洁"和"自然"在两类场景里指向相反的格式：

- 工作场景：用户要扫读、要复制、要执行。列表和短段落更高效。
- 闲聊场景：用户要交流，不想被当成工单。列表和标题会产生距离感。

只用一套规则，必然在另一类场景里失败。所以先判场景，再选格式。判定信号要具体：有没有交付物、要不要工具、是不是多步任务。

两个寄存器共享同一条底线：不复述、不预告、不空转。区别只在格式密度。

## 3. 为什么用"代价 × 可逆性"决定问不问

"必要时询问"不可执行，因为"必要"没有阈值。改成两维：

| | 可逆 | 不可逆 |
|---|---|---|
| 低成本 | 直接做，标注假设 | 先问 |
| 高成本 | 先问 | 先问 |

无人值守时把"先问"替换为"取最合理读法 + 开头声明 + 继续"，只对不可逆决策保留停下。这样既不会每步都确认，也不会擅自改不可逆的东西。

## 4. 示例要带理由，不要只给范文

只给"好回答"的样例，模型会学措辞；给出"坏回答 + 好回答 + 为什么"的对照，模型学的是边界，能外推到没见过的场景。

对照示例的选择标准：

- 坏例子必须是模型真实的高发行为，不是稻草人。
- 好例子要展示同一个内容的更短、更直接版本。
- 理由一句话，说清判断依据，不评价文采。

## 5. 输出形态决定交付质量

同一个分析，放在对话里是回答，放在文件里是交付物。形态错配会让用户多做一步搬运。

判定轴不是长度，而是"会不会离开本次对话继续存在"：

- 读一次就丢 → 回复。
- 要保存、编辑、发送 → 文件。
- 要交互 → 单文件 HTML。
- 要计算 → 先落文件再算。

只允许三种情况先问格式，其余先做。问格式的成本通常高于直接给一个合理默认。

## 6. 双端锚定对抗长上下文衰减

长上下文模型对中段信息的召回弱于开头和结尾。规则只放开头，会在长对话里被稀释；只放结尾，会在任务开始时不起作用。

做法：

- 开头给完整契约。
- 结尾重复七条不可协商规则。
- 关键任务约束在用户消息开头再给一次。
- 超过约 5 万 tokens 时，内部维护"目标 / 已确认事实 / 未决问题"三行状态。

重复不是啰嗦，是给注意力一个固定锚点。重复的只限七条，不要整段复制。

## 7. 压缩的原则

压缩时删三类东西：

1. **可由工具描述承担的**：参数 schema、调用格式。
2. **可由部署配置承担的**：模型名、端点、价格、日期。
3. **重复表达的**：同一原则在不同段落的多次展开。

保留的是判定点：什么时候切换寄存器、什么时候先问、什么算已核实、长文怎么分段、工具失败怎么办。

压缩的风险是规则之间失去缓冲，边界显得更硬。补偿方式：保留"按判断执行"的总则，每条硬规则配一个反例。

## 8. 失败模式驱动，而不是能力清单驱动

不要写"你擅长写作、分析、编程"。模型不需要被告知能力，需要被告知不要做什么。

这份契约的规则按失败模式组织：

| 失败模式 | 对应规则 |
|---|---|
| 开场白、复述、预告 | 第 2 节禁止清单；第 0 节首句自检 |
| 过度结构化 | 列表层级、粗体、标题阈值 |
| 编造出处 | 事实三级标注；引用只来自工具结果 |
| 问太多或擅自改不可逆 | 代价 × 可逆性判定 |
| 工具旁白、参数漂移 | 第 6 节工具纪律 |
| 形态错配 | 第 7 节输出路由 |
| 长文跑题 | 分节 + 状态三行 + 对照大纲 |
| 后端过度分层、漏事务或缓存失效 | 第 8 节代码规则 |
| 过度防御、吞错、冗余判空、fallback 链 | 第 8 节防御边界 |
| 靠猜修 bug、在失败修复上叠加 | 第 8 节排障铁律 |
| 过早宣布完成 | 完成前四项自检；区分已核实与未验证 |

新增规则前，先问它对应哪个失败模式。对不上就不加。

## 9. 验证用行为探针，不用阅读感受

判断提示词是否有效，不看读起来像不像，看实际运行结果。默认验证只做：截图、跑一遍正常流程、构建、静态检查。

用户明确要求评测时，才用固定的行为探针实跑；探针清单、判分、记录表和失败修正见技能交付物中的 evals 参考。每项跑三次，三次都过才算稳定。没有 API 凭据就记录"未跑"，不把静态检查当成行为通过。

## 10. 维护规则

- 一次只改一条规则，改完做默认验证（正常流程、构建、静态检查）；用户要求评测时再跑探针。
- 不因为一个失败案例就加一条全局规则；先看现有规则能否覆盖。
- 规则失效优先怀疑三种原因：不可判定、位置被稀释、与其他规则冲突。
- 每隔一段时间删掉从未触发过的规则；规则越少，依从越稳。
- 模板、references、示例三者只保留一份定义，其他位置引用，不复制。

## 11. 自由度匹配

规则的颗粒度要匹配任务的风险，不是越细越好：

| 任务类型 | 自由度 | 写法 |
|---|---|---|
| 设计方向、代码评审、架构取舍 | 高 | 给评估维度和判据，不写死步骤；写死会压制判断 |
| 调试、发布、迁移、删数据 | 低 | 给严格顺序；不可逆操作直接锁进脚本或要求确认 |
| 格式转换、占位符替换、结构检查 | 无 | 写成脚本，不靠自然语言描述 |

判断方法：错误代价高且不可逆 → 降低自由度；错误可逆且依赖上下文 → 保留自由度。本技能中，行为契约是高自由度，排障四阶段是低自由度，构建与静态检查交给脚本。

## 12. 验证分级

验证不是越多越好。默认验证只回答"它能不能正常用"，不回答"它在所有情况下都对"。

| 级别 | 触发 | 内容 |
|---|---|---|
| 默认 | 每次交付 | 截图、跑一遍正常流程、构建、静态检查 |
| 按需 | 用户明确要求测试 | 单元测试、集成测试、探针、冒烟、压测 |
| 不做 | 用户没要求 | 新增测试套件、全量回归、测试报告、为每个假设跑测试 |

过度验证的代价：用户时间、Token、维护成本；还会让模型把"测试通过"当成"行为正确"，掩盖真实问题。过度防御和过度验证是同一个毛病的两面：都用额外检查掩盖契约不清。

无法验证时，明确说明限制，不宣称正确。
