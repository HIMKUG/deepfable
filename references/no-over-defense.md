# 不过度防御

> 何时读：写或审业务逻辑、API handler、错误处理，重构嵌套 try/catch 或 fallback 链时。读完产出：边界校验清单、错误传播路径、删掉的冗余检查。

## 目录

- 1. 只在边界防御
- 2. 解析，而不是层层校验
- 3. 快速失败，让错误向上传播
- 4. 不写推测性 fallback 链
- 5. 用类型或断言排除不可能状态
- 6. 对照示例
- 7. 适用与例外
- 8. DeepSeek 高发问题
- 9. 检查清单
- 10. 与验证策略
- 11. 最小改动顺序

只在不可信边界防御；内部信任类型和调用方契约；解析一次；快速失败。过度防御会把真实 bug 藏进静默默认值，还让代码难以阅读。

## 1. 只在边界防御

不可信边界：

- HTTP 请求、表单、CLI 参数
- IPC、消息队列
- 文件、环境变量
- 第三方 API 响应
- 数据库读出的无类型 JSON

边界内：内部模块、领域逻辑、私有函数、已经解析过的 DTO。这里信任类型签名和调用方契约，不重复 `if (!arg)`、`?.`、默认值。

## 2. 解析，而不是层层校验

- 在入口一次性把宽松输入收窄为严格类型或领域对象。
- 不把半验证对象传进深层业务逻辑，让每个消费者再检查一遍。
- 用类型表达非空、枚举、范围、ID 格式；动态语言用 schema 解析（pydantic / zod 一类）。
- 解析失败立即报错，不返回部分对象或空默认值。

## 3. 快速失败，让错误向上传播

- 内部调用不写 `try/catch` 只为了 log 一下再返回 `null`、`[]`、`""`、`false` 或 `unwrap_or_default()`。
- 让异常或 `Result` 向上，在顶层统一处理一次。
- 内部只在三种情况捕获：有明确策略的可恢复错误（重试/降级）、资源清理（`finally`）、把底层错误翻译成领域错误并保留 cause。
- 不吞错；不 `except: pass`；不把失败伪装成空结果。

## 4. 不写推测性 fallback 链

坏：

```typescript
const name = data?.user?.name ?? data?.name ?? "Unknown"
```

这段代码在猜数据形状：三个来源都可能，缺了就填默认值，真实契约被掩盖。

好：

```typescript
type OrderView = { user: { name: string } }
function displayName(order: OrderView): string {
  return order.user.name
}
```

定义一个规范形状；缺失就在边界解析时报错。默认值只用于真正可选的业务语义，不用于掩盖契约不清。

## 5. 用类型或断言排除不可能状态

- 让非法状态不可表示：枚举、联合类型、非空 ID、品牌类型、值对象。
- 类型系统覆盖不到的地方，用断言并在失败时立即停止。
- 不写"理论上不会发生"的恢复分支；那种分支一旦执行，说明假设已经错了。

## 6. 对照示例

**坏：**

```typescript
function getUserEmail(user?: User | null): string {
  try {
    if (!user || !user.profile) return ""
    return user.profile.email ?? "none@example.com"
  } catch {
    return ""
  }
}
```

**好：**

```typescript
function getUserEmail(user: ValidatedUser): string {
  return user.profile.email
}
```

差别不在代码长度，而在契约：好版本要求调用方先完成解析；坏版本用三层默认值掩盖了"什么时候允许没有 email"这个业务问题。

## 7. 适用与例外

适用：内部模块、领域逻辑、已解析对象、私有函数。

仍然需要防御：外部边界、安全敏感解析（权限、路径、SQL、反序列化）、数据迁移的源数据、用户输入。

动态语言没有编译期保证时：边界用 schema 解析，解析后的对象在内部直接使用；内部不变量用断言表达，不做层层 `if`。

## 8. DeepSeek 高发问题

| 问题 | 修正 |
|---|---|
| 每个参数都 `if not x: return None` | 在签名和边界表达非空 |
| `try: ... except Exception: return {}` | 让错误向上，顶层处理 |
| `a?.b?.c ?? default` 链 | 定义规范形状，缺失即失败 |
| 给内部函数加默认参数兜底 | 默认值只用于真实可选语义 |
| service 层重复 controller 的校验 | 边界解析一次，内部信任 |
| 用 `or {}` / `or []` 掩盖缺失 | 缺失即报错 |
| 捕获后只 log 不抛 | 记录后继续向上抛，或翻译成领域错误 |
| 为不可能状态写 else 分支 | 用类型排除或断言 |

## 9. 检查清单

- [ ] 外部输入只在边界校验一次
- [ ] 内部函数没有重复的 null/类型检查
- [ ] 没有 catch 后返回默认值的内部调用
- [ ] 没有多级 fallback 链
- [ ] 非法状态用类型或断言排除
- [ ] 顶层有唯一错误边界，内部错误能向上到达

## 10. 与验证策略

不要为了证明防御正确而加测试。默认只做：截图、跑一遍正常流程、构建、静态检查。用户明确要求时才写测试或跑探针。

## 11. 最小改动顺序

改动从小到大，逐级判断：

1. 不改：现有行为已经满足要求。
2. 改常量、配置或一个现有值。
3. 扩展已有函数或模块。
4. 在旁边加一个新函数。
5. 加一个新文件或模块。
6. 加抽象、接口或间接层。
7. 加依赖。

往上走之前，写清更便宜的方案为什么今天不够，点名真实符号和调用点。写不出这句话，就不该往上走。

- 先查项目已有实现、现成库、开源方案或插件；够用就复用，不重造。这一步要轻，不要变成大范围调研。
- 只在第 2–3 次复用或明显可预见时抽象；一次性逻辑不预抽象。
- 不写只转发参数的包装；直接调用。
- fallback 只在能说出需要的具体环境时加；"以防万一"不算环境。
- 只捕获会处理的错误；不 log 后原样重抛，不吞错返回默认值。
- 移动或合并代码时保留原有校验；删掉每一条校验都要有理由。
