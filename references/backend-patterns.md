写服务端代码时的默认判断。原则是**按复杂度选模式**：三张表的原型不需要仓储层，多团队维护的系统不能把 SQL 写在控制器里。

## 1. 分层

```
HTTP / 控制器  →  服务（业务规则）  →  仓储（数据访问）  →  数据库
       ↑
   中间件（认证、日志、限流）
```

- 控制器只做三件事：解析输入、调用服务、映射响应。不写 SQL，不写业务分支。
- 服务层持有业务规则和事务边界；不直接依赖框架的请求对象。
- 仓储层封装查询；返回领域对象或明确的 null，不返回框架特有的响应结构。
- 中间件处理横切关注点：认证、请求 ID、日志、限流。

判断是否需要分层：如果同一段查询被两个以上入口复用，或业务规则开始出现在路由里，就分层。否则先保持简单。

## 2. API 契约

- 资源用名词复数：`/api/markets`、`/api/markets/:id`。
- 动词交给 HTTP：GET 读、POST 建、PUT 全量替换、PATCH 部分更新、DELETE 删。
- 过滤、排序、分页用查询参数；分页优先游标，数据量大时不用 offset。
- 状态码要准确：201 创建、204 无内容、400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、422 语义错、429 限流、500 未知。
- 响应结构稳定：成功 `{ data }`，失败 `{ error: { code, message, details? } }`。同一错误不要两种形状。
- 输入校验在边界完成；校验失败返回字段级错误，不进入业务层。

## 3. 数据访问

- 只取需要的列。`SELECT *` 在宽表上会拖慢查询并放大序列化成本。
- 循环里访问数据库就是 N+1。改成一次批量查询，再用 map 组装。
- 多写操作放在一个事务里；事务边界在服务层，不在仓储方法内部随意开。
- 分页查询要有稳定排序键，否则翻页会重复或漏行。
- 连接池按并发配置；不要在请求里新建连接。
- 迁移和代码一起版本化；破坏性变更分两步（先加后删）。

## 4. 缓存

- 先问：没有缓存会怎样？答不出具体瓶颈就不加。
- cache-aside 是默认：读缓存 → 未命中查库 → 回填；写操作后失效对应键。
- 每个键都要有 TTL；没有失效方案的缓存等于脏数据。
- 键名带版本和实体：`v1:market:{id}`。改结构时换版本，避免旧值污染。
- 只缓存可重建的数据；不作为唯一数据源。
- 热点键加随机抖动，避免同时过期造成击穿。

## 5. 错误处理

- 区分**可预期错误**（校验、未找到、无权限、冲突）与**未知错误**。
- 可预期错误带状态码和用户能理解的 message；未知错误记录完整堆栈，对外只返回通用信息。
- 不把堆栈、SQL、连接串、密钥、内部路径返回给客户端。
- 一个集中式错误映射，不在每个 handler 里重复 if/else。
- 内部调用让错误向上传播；不 catch 后返回默认值，也不吞错继续执行。
- 记录错误时带 request ID、用户 ID（脱敏）、路由、耗时。

## 6. 重试与幂等

- 只重试幂等操作（GET、幂等 PUT/DELETE、带幂等键的 POST）。
- 指数退避 + 上限 + 抖动：1s、2s、4s，最多 3 次。
- 不重试参数错误、认证失败、4xx。
- 支付、下单、消息投递用幂等键；服务端按键去重。
- 重试要有总时限，避免请求堆积。

## 7. 认证、授权与限流

- 认证在边界完成一次；下游信任已解析的身份，不重复解 token。
- 授权默认关闭：先确认有权限，再执行；不用"没匹配到禁止规则就放行"。
- 角色到权限的映射集中管理，不散落在 handler 里。
- 限流用共享存储（Redis、网关、平台原生限流），不用进程内计数：进程内计数在部署后重置、多副本各算各的、serverless 下等于没有。
- 限流键按用户 + 路由 + IP 组合；返回 429 和重试时间。

## 8. 后台任务

- 请求里只入队，不阻塞等待。
- 任务要幂等；失败重试有上限；超过上限进死信队列并告警。
- 任务载荷只放 ID 和必要参数，不放完整对象快照。
- 长任务拆分并记录进度；支持取消。

## 9. 可观测性

- 结构化日志：时间、级别、request ID、路由、耗时、结果；一行一个 JSON。
- 不记录密码、token、卡号、完整身份证号；需要排查时记录末四位或哈希。
- 关键路径打点：入口、外部调用、数据库、队列。
- 错误日志包含足够上下文，但可被普通开发者阅读，不需要复现环境。

## 10. 审查清单

- [ ] 控制器里没有 SQL 和业务分支
- [ ] 查询只取需要的列，没有循环查库
- [ ] 多写操作在事务内
- [ ] 错误形状统一，未知错误不泄露内部信息
- [ ] 重试只用于幂等操作，且有上限和退避
- [ ] 限流使用共享存储
- [ ] 缓存有 TTL 和失效路径
- [ ] 日志含 request ID，无敏感字段
- [ ] 新接口有权限检查和输入校验
- [ ] 破坏性变更可回滚

## 11. DeepSeek 高发问题

| 问题 | 修正 |
|---|---|
| 过度分层：小项目也上 repository + service + DTO | 按复用与团队规模决定，不默认全套 |
| 控制器里直接查库 | 查询下沉到仓储，业务规则上移 |
| `SELECT *` + 循环查关联 | 指定列 + 批量查询 |
| 所有错误都返回 500 或都返回 400 | 按语义映射状态码 |
| 把堆栈/SQL 拼进响应 | 对外通用信息，内部记录详情 |
| 缓存只写不失效 | 加 TTL + 写后失效 |
| 重试 POST 下单 | 加幂等键 |
| 进程内 Map 做限流 | 换共享存储 |
| 日志打印整个请求体 | 白名单字段 + 脱敏 |

## 12. MCP 工具设计

要写 MCP server 时，加载完整 `mcp-builder` skill；这里是最小判据。

- **命名**：统一前缀 + 动作，例如 `github_create_issue`、`github_list_repos`；名字要能被模型直接选中。
- **描述**：说清何时用、输入是什么、返回什么、失败怎么处理；不要写营销文案。
- **Schema**：严格类型、枚举、必填项、默认值；边界解析一次，内部信任。
- **输出**：只返回相关字段；大结果分页或过滤，不把整个 API 响应倒进上下文。
- **错误**：可操作，告诉调用方下一步怎么做；不泄露内部堆栈和密钥。
- **认证**：密钥走环境变量；不出现在工具描述、日志或返回内容里。
- **传输**：本地用 stdio；远程用 streamable HTTP，优先无状态 JSON，便于扩展。
- **版本**：新项目用 TypeScript SDK v2（`@modelcontextprotocol/server`）；已有 v1 项目不要混用，先提示迁移。
- **验证**：用 MCP Inspector 跑真实调用；按 `mcp-builder` 的评估脚本检查工具可用性，不只看 server 能启动。
- **覆盖 vs 工作流**：不确定时优先覆盖完整 API；高频组合再抽专用工作流工具。
