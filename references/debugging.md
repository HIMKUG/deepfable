# 系统化排障

> 何时读：出现 bug、测试失败、行为异常、性能问题，且在提出修复之前。读完产出：一句话根因、可复现证据、验证结果。

适用于任何技术问题：测试失败、线上 bug、行为异常、性能问题、构建失败、集成错误。

排障不是过度测试：只做定位所需的取证；不为每个假设跑全套测试。默认验证是复现、运行、构建或静态检查；测试只在用户明确要求时进行。

## 铁律

**没有完成根因调查，不提出修复。**

症状修复不算修复。看起来"先改一下试试"的冲动，正是需要停下来的时候。越急越要走流程：猜-改-试的来回次数通常多于一次系统排查。

## 四阶段速查

| 阶段 | 关键动作 | 完成标准 |
|---|---|---|
| 1 根因调查 | 读完整错误、稳定复现、查最近改动、边界取证、回溯数据流 | 知道是什么、为什么 |
| 2 模式分析 | 找可工作的同类实现、完整读参照、列出差异 | 能说出关键差异 |
| 3 假设验证 | 单一假设、最小改动、一次一个变量 | 假设成立或换新假设 |
| 4 实施 | 先取得可复现证据、只修根因、按需验证 | 问题消失、相关检查通过 |

## 四阶段

### 阶段 1：根因调查

1. **完整读错误**。不跳过 warning，不只看最后一行。记下文件、行号、错误码、调用链。
2. **稳定复现**。写下精确步骤；能否每次触发。不能复现就继续收集数据，不猜。
3. **查最近改动**。`git diff`、最近提交、新依赖、配置变更、环境差异。
4. **多组件系统在边界取证**。在每一层记录输入、输出、配置传递：
   - 请求进了服务吗？
   - 服务拿到正确参数了吗？
   - 数据库收到什么查询？
   - 返回值在哪一层变形？
   跑一次拿到"哪一层断"的证据，再进入该层。
5. **沿数据流回溯**。坏值从哪里产生？谁把它传进来？一直追到源头，在源头修，不在症状处修。

### 阶段 2：模式分析

1. **找可工作的同类实现**。同一个代码库里，哪段类似代码是正常的？
2. **完整读参照实现**。不跳读、不"大致理解后自己改"。模式类问题，读一半必然出错。
3. **列出所有差异**。配置、版本、顺序、边界条件、默认值；不要假设"这个不可能有影响"。
4. **确认依赖与假设**。需要哪些服务、权限、环境变量、数据前置条件？

### 阶段 3：假设与验证

1. **一次一个假设**。"我认为 X 是根因，因为 Y。"写下来，要具体。
2. **最小改动验证**。只改一个变量；不顺手修别的。
3. **验证后再继续**。成立 → 阶段 4；不成立 → 形成新假设，不在旧修复上叠加。
4. **不知道就说不知道**。不假装理解；查文档、读源码、问人。

### 阶段 4：实施

1. **先拿到可复现证据**。最小复现命令、日志或一次性脚本。没有可复现证据就不算定位。用户明确要求自动化测试时，才把它写成测试。
2. **只改根因**。一次一个改动；不做"顺便重构"。
3. **验证**：问题确实消失；构建、类型或静态检查通过。用户要求测试时，新测试通过、原测试不挂。
4. **失败就回阶段 1**，带着新信息重查；不要在未验证的修复上继续加。

## 三次失败 → 质疑架构

连续 3 次修复失败，停止修第 4 次。典型信号：

- 每次修复都在别处暴露新的共享状态或耦合问题。
- 修复需要大范围重构才能落地。
- 每修一个症状，另一个地方冒出来。

这说明假设没错，架构错了。停下来讨论是否换方案，不要继续打补丁。

## 红旗

出现以下想法，立刻回到阶段 1：

- "先快速修一下，之后再查。"
- "改 X 试试，看行不行。"
- "一次改几处，看哪个生效。"
- "跳过复现和取证，直接改。"
- "大概是 X，先修这个。"
- "我没完全理解，但这样可能行。"
- "再试一次"（已经试过两次以上）。
- 还没追踪数据流就开始列解决方案。

## 协作信号

用户或同事的这些话，说明流程走错了，立刻回到阶段 1：

| 信号 | 含义 |
|---|---|
| "是这样吗？" | 你在假设，没有验证 |
| "能看到……吗？" | 应该先在组件边界取证 |
| "别猜了" | 没有理解根因就提修复 |
| "再想深一点" | 质疑根本假设，不要继续打补丁 |
| "卡住了？" | 当前方法无效，换排查路径 |

不要解释为什么你的方法合理；先补证据。

## 常见合理化

| 借口 | 现实 |
|---|---|
| 问题很简单，不用流程 | 简单问题也有根因；流程在简单问题上很快 |
| 紧急，没时间 | 系统排查比反复试错快 |
| 先试一下再调查 | 第一次修复会设定后续方向 |
| 先猜一个修复，再补证据 | 第一次修复会设定方向；先取证 |
| 一次改多处省时间 | 无法归因，还会引入新 bug |
| 参照太长，大致改改 | 理解一半必然出错 |
| 我看到问题了，直接修 | 看到症状不等于理解根因 |

## "没有根因"的处理

系统排查后，如果问题确实是环境、时序或外部依赖：

1. 记录排查过的层次与证据。
2. 加适当的处理：重试、超时、降级、更清楚的错误。
3. 加日志或监控，供下次定位。

但先确认：大多数"没有根因"其实是调查不完整。

## 支撑技巧

- **回溯法**：从报错点沿调用栈反向追，找到第一个把坏值引入的位置。修在引入点，不在报错点。
- **分层校验**（defense in depth）：根因修好后，在输入边界、服务层、数据层各加一层校验。校验层是兜底，不能代替根因修复，也不能用来掩盖问题。
- **条件等待**：用轮询条件替代固定 `sleep`；设超时和失败信息。固定等待会让流程变慢且不稳定。

## 验收

- 能用一句话说清根因（哪个输入、哪行代码、哪个配置导致）。
- 有一个在修复前失败、修复后通过的用例。
- 相关构建、类型或静态检查通过；用户要求测试时，原有测试全绿。
- 能说明为什么之前没被发现，以及是否需要加防护。

## 与模板的对应

- 铁律与四阶段 → 模板第 8 节"代码与排障"的排障条目。
- 一次一个假设、一次一个改动 → 第 8 节与第 5 节。
- 验证后才宣称完成 → 第 0 节自检与完成前检查。
- 三次失败质疑架构 → 第 8 节最后一条。
