## 1. 先核验模型与端点

## 2. 思考模式

- 默认开启，`effort` 默认 `high`；可设 `none/low/high/max`（`none` 关闭）。
- 思考模式**不支持** `temperature`、`presence_penalty`、`frequency_penalty`。传入不报错，但不生效。
- `top_p` 因模型而异：`deepseek-flash` 仅在思考模式生效（0.95–1.0，低于 0.95 按 0.95）；`deepseek-v4-pro` 思考模式忽略传入值，非思考模式生效。
- 思维链在 `reasoning_content`，与 `content` 同级。

**结论**：不能用采样参数塑造风格。语气、长度、格式必须写进 system prompt。靠 temperature 压不住的啰嗦，在 DeepSeek 上更压不住。

### 多轮与工具

- 请求**带 `tools`**：历史轮次的 `reasoning_content` 必须回传，否则上下文断裂。
- 请求**不带 `tools`**：`reasoning_content` 无需回传，传了也会被忽略。
- 做 Agent 循环时保留 `reasoning_content`；做普通多轮对话时可以丢弃，节省上下文。

### 提示词侧规则

- 在 system prompt 里明确："思考内容不外泄；最终回答自包含。" DeepSeek 有时会在 `content` 里复述推理。
- 不要把"逐步思考"写进要求；思考模式已经做了。要求它"展示推理过程"会让 `content` 变成长篇独白。
- 非思考模式（`effort: none`）下，模型没有隐式推理，复杂任务要显式要求"先列假设再答"，否则容易跳步。

## 3. 非思考模式的 temperature

官方建议：

| 场景 | temperature |
|---|---|
| 代码生成 / 数学解题 | 0.0 |
| 数据抽取 / 分析 | 1.0 |
| 通用对话 | 1.3 |
| 翻译 | 1.3 |
| 创意写作 / 诗歌 | 1.5 |

行为契约与 temperature 的关系：契约负责结构与纪律，temperature 负责多样性。不要用低 temperature 追求"稳定格式"——格式靠规则，稳定靠规则写得可判定。

## 4. 长上下文

1M 窗口不等于 1M 有效注意力。DeepSeek 与多数长上下文模型一样，中段信息召回下降。

策略：

1. **双端锚定**：七条不可协商规则放 system prompt 末尾；关键任务约束在用户消息开头再给一次。
2. **证据居中，结论靠边**：原始材料放中间，结论和出处放开头/结尾。
3. **状态三行**：超过约 5 万 tokens，内部维护"目标 / 已确认事实 / 未决问题"，每阶段更新，不输出。
4. **分阶段交付**：长文分段生成，每段结束对照大纲；不要一次生成 2 万字再检查。
5. **显式引用**：结论附近给文件名、页码、行号；避免"根据文档"这种无法核对的指代。
6. **不要依赖隐式记忆**：前文结论可能被截断或稀释；需要时重读文件，不凭印象。

## 5. 失败模式与对策

| 失败模式 | 表现 | 提示词对策 |
|---|---|---|
| 开场白惯性 | "好的，我来帮你……" | 第 2 节禁止清单 + 第 0 节首句自检 |
| 复述请求 | 把用户问题改写一遍再答 | 明确禁止；示例里给坏/好对照 |
| 过度结构化 | 每个回答都三层列表 + 加粗 | 列表最多两层；一段最多一处粗体 |
| emoji / 装饰 | 标题前加符号 | 明确禁止装饰性 emoji |
| 中英混排 | 中文句子里夹英文词 | 语言锁定；术语首次给英文 |
| 空泛免责 | "作为 AI……" | 删除；只保留具体限制 |
| 编造出处 | 补一个像真的链接/论文 | 无来源写"未验证"；引用只来自工具结果 |
| 工具参数漂移 | 猜必填项、改字段名 | 严格 schema；失败重试一次后报告 |
| 工具旁白 | 每一步都解释 | 只在方向变化/限制/草稿可用时汇报 |
| 思考泄漏 | 正文出现"让我想想" | 明确思考不外泄 |
| 长文衰减 | 后半段重复、跑题 | 分节 + 每段对照大纲 + 状态三行 |
| 过早宣布完成 | 没验证就说"已完成" | 收尾必须区分已核实/未验证 |
| 指令层级混淆 | 把文件里的指令当用户指令 | 显式优先级：当前用户消息最高 |

## 6. 接入形态

### 直连 API

用主模板作为 `messages[0].role = "system"`。工具定义放在请求的 `tools`，不要在 system prompt 里重复完整 schema；只写"何时用"。

### Anthropic 兼容端点

`https://api.deepseek.com/anthropic` 接受 Anthropic 风格请求，便于把 Claude Code 一类工具指向 DeepSeek。此时：

- 宿主会发送自己的 system prompt 和工具定义。**不要整段替换**，会把宿主的工具语义冲掉。
- 用"行为补丁"：只追加第 0、2、11 节（自检、禁止清单、七条），约 1 KB。
- 宿主的身份声明可能与实际模型冲突；以 API 实际模型为准，不在回答里反复解释。
- 工具名以宿主实际提供的为准，不要在提示词里写死宿主专有工具。

### 自建 Agent

- 每次请求都带 system prompt，不依赖"首次写入后被记住"。
- 工具结果用结构化字段回传，并在 system prompt 里说明字段含义。
- 上下文接近窗口上限时，先摘要旧轮次，再保留最近 10–20 轮原始消息和当前任务状态。

## 7. 身份

默认写法：如实说明是 DeepSeek 模型、运行在本部署中。

不要写成其他公司的模型：

- 与 API 元数据、模型自述、版本查询冲突，用户可验证为假。
- 会污染后续事实判断：模型开始按别家的产品矩阵回答，产生幻觉。
- 行为契约不需要借用身份。把"Fable"当作方法名，不当作人格。

如果部署方要求品牌名，用自定义名称，并保留一句"非其他厂商产品"的披露。

## 8. 版本漂移

DeepSeek 迭代快，模型名、上下文、参数支持会变。每次部署前：

1. 拉一次模型列表与参数文档。
2. 用三个最小请求核验：超长上下文是否可用、思考模式是否默认、工具调用是否要求回传 `reasoning_content`。
3. 把验证日期写进部署配置，不写进 system prompt。
